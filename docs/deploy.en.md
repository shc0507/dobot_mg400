# Host deployment

[Project home](../README.en.md) · [Installation](#installation-and-updates) · [Configuration](#configuration-file) · [Routine commands](#routine-commands) · [Connection lock](#panel-connection-lock) · [Migration](#migration-to-a-new-host)

This page explains how to install, update, and run the project's services on a Linux host.
Deployment does not depend on a specific platform. For Olares networking, code access, and USB troubleshooting, see [Olares configuration and maintenance](olares.en.md).

## Prerequisites

- The host runs Linux and systemd.
- `/usr/bin/python3` is Python 3.12 or later.
- Git, `setpriv`, and [uv](https://docs.astral.sh/uv/getting-started/installation/) are installed on the host.
- The host can access PyPI. `uv sync` downloads dependencies from PyPI.
- A host network interface connects directly to the robot and has address `192.168.1.10/24`.
- This interface can connect to the robot's TCP ports `29999`, `30003`, and `30004`.
- For cameras, download the Linux program for version 1.9.14 from the [go2rtc releases page](https://github.com/AlexxIT/go2rtc/releases/tag/v1.9.14).
- For microscope recordings, `ffmpeg` and `ffprobe` are installed on the host. On Debian or Ubuntu, the `ffmpeg` package supplies both programs: `apt-get install ffmpeg`.

## Installation and updates

Run the commands in this section as root.
Before an update, stop the services with `mg400ctl stop all`.

1. Get the code. For the first installation, run:

   ```sh
   git clone https://github.com/shc0507/dobot_mg400.git /opt/mg400
   ```

   For an update, switch to the target commit:

   ```sh
   git -C /opt/mg400 fetch origin
   git -C /opt/mg400 switch --detach origin/main
   ```

   If the host cannot access GitHub, get the code through a Git bundle. See [When GitHub is unavailable on Olares](olares.en.md#when-github-is-unavailable).

2. Run the installer:

   ```sh
   /usr/bin/python3 /opt/mg400/deploy/install.py --caddy /path/to/caddy
   ```

   On the first installation, `--caddy` gives the Caddy 2 program. Later runs reuse the installed program.
   For cameras, add `--go2rtc <go2rtc 程序路径>` with the go2rtc program path on the first installation.
   For Toupcam, add `--toupcam PATH` with the verified library described below.
   With `--dry-run`, the installer only lists its steps and does not change the host.

3. After the first installation, edit the configuration as described in [Configuration file](#configuration-file).
4. Start or restart services. See [Routine commands](#routine-commands).

The installer works in this order:

1. Check the Python version, uv, the configuration file, and any independently running gripper collection processes.
   Also check the service registry, selection, selected units, and udev templates.
   If `--toupcam` is supplied, check its source, destination, and pinned SHA-256.
   If assets are requested or `vision` is enabled, also check the asset manifest, destination paths, and local files.
   If `microscope` is enabled, look for `ffmpeg` and `ffprobe` in the default `PATH` of systemd services. If a program is missing, show a notice, but do not stop the installation.
   If a check fails, leave the host unchanged.
2. Create the configuration file or add missing entries. Keep nonempty values.
   Remove old service `*_TOKEN` entries, except `MG400_GATEWAY_TOKEN`, and empty entries that the example does not contain.
3. Create the directories under `/var/lib/mg400`. Refuse symbolic links there.
4. Run `uv sync` from the service registry, with dependency groups only for enabled services.
   By default, install the stage and tool dependencies in `/opt/mg400/.venv`.
5. Install requested external assets and the required weights when `vision` is enabled. Check size and SHA-256 before atomic replacement.
6. If cameras are configured, install go2rtc and generate `go2rtc.yaml`. Otherwise, remove the old `go2rtc.yaml`.
   If `--toupcam` is supplied, install the library bytes verified in step 1.
7. If selected services have udev templates, render and install their rules. Reload the rules, then trigger udev events for USB devices.
8. Install selected service definitions, reload systemd, and enable the gripper collection request listener.
9. Create the `mg400ctl` and `labctl` links.

The installer does not start, stop, or restart services.
You must stop services before updating the code. Running services can read a mixture of old and new files.
After the update, start services, then reload the Lab Console if it is open.
Do not edit files in `/opt/mg400`. Modified files can cause `git switch` to abort the update.

## Toupcam library

Get `linux/x64/libtoupcam.so` from the [Toupcam 59.30594.20260120 SDK archive](https://www.touptekphotonics.com/downloads/software/toupcamsdk.20260120.zip).
Keep the archive and library outside Git. Pass the extracted library path to the installer:

```sh
/usr/bin/python3 /opt/mg400/deploy/install.py --toupcam /path/to/linux/x64/libtoupcam.so
```

The required SHA-256 is `5ba51b66bb9e2901e769fa1d5d5ae88c359269ea7fb20358335462c531a3e997`.
The installer refuses a mismatch, a symbolic link, or a nonregular file before changing the host.
It copies the verified bytes atomically to `/usr/local/lib/mg400/libtoupcam.so`, owned by `root:root` with mode `0755`.
It does not load the library or open a camera. Add `--dry-run` to validate and list the steps without changing files.
Without `--toupcam`, an existing library stays unchanged.

Without the library, the installer prints a warning and installs the microscope service without its camera.
An installed library must have the pinned hash and safe ownership and permissions.
The installer rejects untrusted destination directories before changing the host.
Existing destination directories must be root-owned, traversable by UID `1000`, and not writable by the service or other users.
The microscope service owns this camera and furnace recordings. Its unit sets `Environment=LD_LIBRARY_PATH=/usr/local/lib/mg400`.
The existing `config/udev/70-mg400-microscope.rules.in` template grants the service group `0660` access to C3CMOS05100KPA USB3 `0547:1375` and USB2 `0547:1376` devices.
The installer renders this template for the microscope service.
Do not install the vendor's `99-toupcam.rules`: it grants broad `0666` access to vendors `0547` and `04b4`.

## Service registry

`deploy/services.toml` contains a `[[service]]` entry for each implemented service.
The installer, `mg400ctl`, and `labctl` share this registry.
Add each new service entry together with its unit files.

| Field | Meaning |
| --- | --- |
| `name` | Service name used by commands |
| `units` | systemd unit list. Start item 1, whose dependencies start the remaining units |
| `optional` | `true` for optional services, `false` for mandatory services |
| `venv` | Python environment, either `.venv` or `.venv-vision` |
| `groups` | uv dependency groups for this service |
| `port` | Primary TCP port, or 0 for no TCP port |
| `assets` | Asset manifest names owned by this service |

`web`, `stage`, `camera`, `collector`, `furnace`, and `microscope` are always mandatory.
`MG400_OPTIONAL_SERVICES` accepts service names from the registry, separated by commas.
The default is empty. Unknown names, duplicates, or empty items cause the installer to refuse installation. Mandatory service names have no effect.
The optional `thermal` service uses the `thermal` dependency group in `/opt/mg400/.venv`.
Add `thermal` to `MG400_OPTIONAL_SERVICES`, preserving other selections, then run the installer.
It installs the thermal USB access rule and prepares `/var/lib/mg400/thermal` with owner `1000:1000` and mode `0750`.
It does not create region coordinates or start the camera. Configure named regions as described in the [thermal guide](thermal.en.md).
The owner starts the service explicitly with `mg400ctl start thermal`. Startup opens the camera automatically.

Use `mg400ctl logs thermal` and `mg400ctl stop thermal` for logs and shutdown.
Stop other camera applications first. Only 1 process can own the P1 camera.

The `furnace` service uses the `furnace` dependency group.
Configure its serial paths before hardware use, then start it explicitly with `mg400ctl start furnace`.
The installer does not start the furnace.

The `microscope` service uses the `microscope` dependency group in `/opt/mg400/.venv`.
Configure the [microscope](microscope.en.md#managed-host-service).
The installer prepares its default calibration, recording, and run directories without replacing imported data.
The owner starts `camera` before `microscope`. The installer does not start either service.

The optional `vision` service uses the `vision` and `vision-gpu` dependency groups in the isolated `/opt/mg400/.venv-vision` environment.
Add `vision` to `MG400_OPTIONAL_SERVICES`, preserving other selections. Run the installer.
It prepares `/var/lib/mg400/vision` with owner `1000:1000` and mode `0750`, and installs the verified `vision-weights` asset.
Without `vision` in the selection, it does not prepare this environment, directory, asset, or unit.

The owner performs the first installation, runs `mg400ctl start vision`, and checks `mg400ctl gpu` on Olares.
See [Vision service](vision.en.md) for runtime settings and [Olares networking](olares.en.md#network) for access rules.

The `orch` service uses the `orchestrator` dependency group in `/opt/mg400/.venv`.
This group includes Flask, waitress, and the `stage`, `thermal`, and `furnace` groups for supported owned demos.
The installer prepares the `runs` and `zones` directories. It does not invent zone configuration or start the service.
The same service serves the [Lab Console](dashboard.en.md#lab-console). It is the only operator web page. It has the Overview, Motion, Cameras, and Furnace + microscope workspaces, and separate motion, heat, and gas stop controls.
The console has no recipe run controls. Use the [recipe service interface](orchestrator.en.md#http-service) to start, abort, and recover runs.

The optional `gateway` service uses the `gateway` dependency group. Its work is postponed. See the [agent gateway](agent-gateway.en.md).
Selecting `gateway` also prepares the `runs` directory for audit records. The installer does not start the gateway.
Every MCP request requires `MG400_GATEWAY_TOKEN`. The installer does not generate it. Set it by hand in the configuration file.

The `proxy` service adds no Python dependency group. On the first installation, supply Caddy 2 through `--caddy PATH` and configure the [single-port entry](olares.en.md#single-port-proxy).
The installer checks the proxy before changing files and never starts the proxy.

The installer combines enabled services' `groups` by `venv` and synchronizes each environment only 1 time.
Synchronization explicitly uses `--no-default-groups` and does not install the project's default dependency groups.
Mandatory services use `stage` and `tools` in `/opt/mg400/.venv`.
Services that select `.venv-vision` use `/opt/mg400/.venv-vision`.
The installer explicitly sets `UV_PROJECT_ENVIRONMENT`. It does not use another environment specified by the caller.

For a service with udev rules, the template path is `config/udev/70-mg400-<name>.rules.in`.
Templates must contain a VID, PID, `MODE="0660"`, and `@SERVICE_GROUP@`.
The installer replaces the placeholder with the group name for GID 1000.
The destination is `/etc/udev/rules.d/70-mg400-<name>.rules`, owned by `root:root` with permissions `0644`.
Only enabled services' templates are installed. A dry run only lists rule installation, reload, and udev event trigger steps for USB devices.

Stop an optional service before removing its name from the setting.
Removing its name does not stop processes or delete existing files or rules.
`start`, `restart`, and `status` use only enabled services.
`stop` and `logs` can still access disabled registered services. `stop all` includes all registered services.
`stop all` skips a unit that systemd reports as not installed and inactive, and prints the unit name.

## External assets

`config/assets.toml` stores 1 table per external asset.
The fields are `url`, `sha256`, `bytes`, `install`, `mode`, `service`, `source`, and `license`.
`install` is an absolute destination path under `/var/lib/mg400/`. `mode` must be `0640` or `0600`.
Asset files and destination directories belong to `1000:1000`. Destination directories have permissions `0750`.
The installer refuses symbolic links in source files, destination files, or their paths.

The initial `vision-weights` entry specifies `chip-arm-yolo26s-seg-v1.pt` in this repository's `vision-model-v1` release.
Its size is 23,393,117 bytes. Its SHA-256 is `0b684c470191540b0cfc8802b0d13149b47d7be76b901ad1dd59882297407a07`.
The destination is `/var/lib/mg400/models/chip-arm-yolo26s-seg-v1.pt`, with permissions `0640`.
The manifest records the license as `AGPL-3.0`, as declared by Roboflow.
Downloads fail if the release does not contain the file.

Assets must belong to an enabled service and appear in its `assets` list.
When `vision` is enabled, installation requires `vision-weights`, even without `--fetch-assets`.
Supply a verified local file with `--asset vision-weights=PATH`, or let the installer download the manifest asset.
With `vision` disabled, `--fetch-assets` skips its weights and explicit `--asset vision-weights=PATH` refuses installation.
Other assets require an explicit request. To download enabled services' assets:

```sh
/usr/bin/python3 /opt/mg400/deploy/install.py --fetch-assets
```

If the installed file matches the manifest size, SHA-256, owner, and mode, the installer keeps it and does not download it again.
Downloads use only HTTPS, including redirects.
The installer writes content to a temporary file in the destination directory, then checks its byte count and SHA-256.
After successful checks and ownership and permission changes, the installer replaces the destination atomically.
If downloading, verification, or permission changes before replacement fail, the original file remains unchanged.

For offline installation, copy the weights to the host through the Drive transfer procedure in [When GitHub is unavailable on Olares](olares.en.md#when-github-is-unavailable).
The local file path can differ from the destination. After enabling `vision`, for example, use `/tmp/chip-arm-yolo26s-seg-v1.pt`:

```sh
/usr/bin/python3 /opt/mg400/deploy/install.py --asset vision-weights=/tmp/chip-arm-yolo26s-seg-v1.pt
```

You can repeat `--asset NAME=PATH`, but specify each asset only 1 time.
When combined with `--fetch-assets`, the local file takes precedence for the same asset.
Local files and downloads use the same size and SHA-256 checks. Do not change the manifest to bypass verification.
With `--dry-run`, the installer only shows planned steps. It does not download, write, or change permissions.
Dry runs still verify specified local files. They cannot confirm remote asset availability.

Run `mg400ctl assets` to check each manifest asset:

- `present`: content, size, ownership, and permissions match the manifest.
- `missing`: the destination file does not exist.
- `mismatch`: content or file attributes differ, the path is unsafe, or the file cannot be read.

The exit code is 0 when all assets are `present`, or 1 otherwise.
This command does not download assets, change files, or start services.

## Configuration file

`/etc/mg400/mg400.env` stores all configuration for this host.
Services read this file at startup. After a change, restart the affected service.
Empty entries use their defaults.
Values must not contain inner quotes or backslashes, except the furnace JSON settings below.
The installer and `mg400ctl` reject lines that systemd could interpret differently.
Only `MG400_FURNACE_GAS_MAP` and `MG400_FURNACE_IDLE_GAS` accept single-quoted JSON objects.
Their inner double quotes remain literal. Escapes, apostrophes, control characters, duplicate keys, and nonfinite numbers are refused.
See [furnace configuration](furnace.en.md#configuration) for syntax and process limits.
Each time it runs, the installer restores this file's owner to `root:root` and permissions to `0600`.

The file contains only hardware facts. Bind addresses, ports, base paths, and service URLs are fixed defaults in the code and the units.
All services listen on `127.0.0.1`. From the VPN, only the proxy port `8080` is open. The VPN is the access boundary, and the services do not check tokens.
The robot connection lock directory is `/var/lib/mg400/locks`. The Lab Console uses the base path `/lab/`.

| Setting | Default | Purpose |
| --- | --- | --- |
| `MG400_PROXY_BIND` | `127.0.0.1` | Numeric proxy listen address |
| `MG400_PROXY_PORT` | `8080` | Proxy port, from `1024` to `65535` |
| `MG400_OPTIONAL_SERVICES` | Empty | Optional service names from the registry, separated by commas |
| `MG400_ROBOT_HOST` | Address in `config/robot.toml` | Robot address |
| `MG400_ROBOT_MAX_SPEED_L`, `MG400_ROBOT_MAX_ACC_L` | `1` | Robot speed cap, integer percentages from `1` to `100` |
| `MG400_ORCH_TOOL_FILE` | `/var/lib/mg400/robot/tool.toml` | Measured tool offset |
| `MG400_CAMERA_DEVICES` | Empty | 1 to 4 distinct camera devices separated by commas. Empty disables cameras |
| `MG400_CAMERA_MODES` | Empty | One approved `WIDTHxHEIGHT@FPS` mode per device, in device order |
| `MG400_STAGE_SERIAL` | Empty | Arduino serial port path. See [Stage configuration](stage-panel.en.md#configuration) |
| `MG400_VISION_WEIGHTS` | `/var/lib/mg400/models/chip-arm-yolo26s-seg-v1.pt` | Verified local model weights |
| `MG400_VISION_DEVICE` | Empty | Select `cuda` when available, otherwise `cpu` |
| `MG400_FURNACE_SERIAL` | Empty | Furnace serial device |
| `MG400_MFC_SERIAL` | Empty | Separate gas-controller serial device |

Configure the furnace caps and gas map as described in [furnace configuration](furnace.en.md#configuration).
Configure microscope device selection, focus limits, and camera streams as described in the [microscope guide](microscope.en.md#contract-service).

Use distinct camera device paths under `/dev/v4l/by-path/`. These paths distinguish cameras of the same model by their USB ports.
The camera service provides only configured streams, named `camera1` through `camera4` in device order.
With an empty mode list, ordinary cameras use `640x480@30`; the configured `MG400_MICROSCOPE_SIDE_STREAM` uses `3840x2160@30`.
An explicit mode list overrides these defaults. Invalid counts, paths, or modes stop installation before host changes.
Only streams with width at most 640 and height at most 480 are preloaded. Larger streams start on demand.
After changing devices or modes, run the installer again to generate a new `go2rtc.yaml`, then restart the cameras.
See [Cameras](olares.en.md#cameras) for approved modes and the tray-camera configuration.

## Routine commands

Run `mg400ctl` as root, for example `sudo mg400ctl status`.
`labctl` uses the same arguments and behavior:

| Command | Effect |
| --- | --- |
| `mg400ctl backup FILE.tar` | Save private host settings and data, excluding process locks |
| `mg400ctl assets` | Check external asset content, ownership, and permissions |
| `mg400ctl gpu` | Read GPU name, used memory, and total memory as UID `1000` |
| `mg400ctl status` | Show the status of all services |
| `mg400ctl start web stage camera` | Start services. Names are `web`, `stage`, `camera`, `collector`, `thermal`, `furnace`, `microscope`, `vision`, `orch`, `gateway`, `proxy`, or `all` |
| `mg400ctl stop all` | Stop services |
| `mg400ctl restart web` | Restart services |
| `mg400ctl logs web -n 100` | Show service logs. Add `-f` for continuous output |
| `mg400ctl terminal` | Open the [interactive terminal](terminal-control.en.md) |
| `mg400ctl mode` | Read the controller mode. See [Switching TCP/IP mode](hardware.en.md#switch-to-tcpip-mode-from-the-server) |
| `mg400ctl camera-url` | Show 1 `/camera/cameraN.mjpeg` link for each camera. If `proxy` is enabled, the links use the proxy address |
| `mg400ctl camera-check` | Check camera devices, services, and capture streams in order. See [Camera failures](olares.en.md#camera-failures) |

`gpu` runs `nvidia-smi --query-gpu=name,memory.used,memory.total --format=csv` as UID `1000`.
It is a read-only diagnostic. It does not start services, load the model, or change GPU settings.
The command receives no host settings.
GPU output alone does not confirm that vision selected CUDA. Check `mg400ctl logs vision` and the service state.

Furnace `stop` and `restart` query live state before changing any selected service.
The check includes mixed lists and `all`, including a disabled furnace selected by `stop all`.
`stop` skips the check only when systemd reports every furnace unit as not installed and inactive. If systemd gives no clear answer, the check runs.
An active sequence or cooling gas plan requires `--force`. Unavailable, malformed, disconnected, or locked status also requires `--force`.
Coordinate with all clients before using `mg400ctl stop furnace --force` or `mg400ctl restart furnace --force`.
Forced shutdown requests that the service stop heat and gas. Verify the stop result. The check is advisory: a sequence can start between the status read and systemd action.
The guard uses the configured IP bind, port, and base path. It accepts `localhost` and maps `0.0.0.0` to `127.0.0.1`, and `::` to `::1`.
It does not use proxies or redirects.
Socket operations time out after `2` s. A `2` s body deadline is checked between returned chunks.
Header and transfer-framing reads use socket timeouts, so this is not a total request deadline.
Responses above `262144` bytes are refused.

Stopping `orch` requests a hold, drains accepted operations, records the final state, and releases service leases.
Its unit uses `TimeoutStopSec=infinity`, so systemd waits for this cleanup instead of imposing a stop deadline.
Restarting the service does not resume saved runs or clear retained zones. Use the [recovery procedure](orchestrator.en.md#http-service).

`terminal` and `mode` use `runuser --pty` to run as UID 1000 in a separate pseudo-terminal.
They read the configuration file and share the robot service's connection lock.
When the robot service stops or restarts, it can take up to approximately 60 seconds to confirm that the robot stopped.
You do not need to start gripper collection manually. The robot service or interactive terminal requests collection when it connects to the robot.

## Panel connection lock

The robot service, interactive terminal, and mode-switch tool acquire a file lock before connecting to the robot.
The robot service's read-only mode also uses this lock.
If another program holds the lock, a new connection returns `Robot controlled by another panel`.
After a normal disconnect, the robot service waits for the feedback thread and command tasks to end before releasing the lock.
If it cannot confirm the stopped state, the robot service stops routine coordinate queries, keeps feedback and the lock, and shows a warning.
Check the robot, then click Recover. Reloading the Lab Console does not clear the warning.

All programs must use the same robot address and the lock directory `/var/lib/mg400/locks`.
The units and `mg400ctl` set this directory. It must support operating-system file locks.
All programs run as UID 1000. Lock file permissions are `0600`.
When running as root, the program refuses lock directories not owned by root.
If an existing lock file has a different owner, the program changes its owner in place and preserves the original file.

Do not remove lock files to release ownership. When a process exits, the operating system releases the locks that process holds.
A process exit does not confirm that the robot stopped.
This lock does not restrict DobotStudio or other hosts. Close other control programs before use.

## Backup

`mg400ctl backup FILE.tar` archives `/etc/mg400/mg400.env` and `/var/lib/mg400` with numeric owners and file modes.
It excludes only `/var/lib/mg400/locks`, which contains process connection locks.
It includes persistent gripper command locks under `/var/lib/mg400/work`, including `gripper_feedback.json.command-lock.json`.
It also preserves furnace state and `.state.json.lock` under `/var/lib/mg400/furnace`.

Stop services, the gripper request listener, and other data writers before a backup, as the migration steps below specify.
The command does not stop them for you.
It refuses missing inputs, symbolic links, special files, directory cycles, and changes detected while reading.
Correct the cause before retrying. Do not remove a safety lock to make a backup pass.

Choose an existing root-owned destination directory that group members and other users cannot write.
The destination must be outside the backed-up paths, and its path must contain no symbolic link or `..` component.
The command refuses to overwrite any existing path, including a broken symbolic link.
It writes a private temporary archive and publishes the destination only after completing the archive.

The archive has owner `root:root` and mode `0600`.
It contains the host settings and data.
Keep these permissions when storing or transferring it, and do not commit it to Git or publish it.

## Migration to a new host

The backup includes the following paths when they exist:

| Path | Content |
| --- | --- |
| `/var/lib/mg400/models/` | Installed model weights |
| `/var/lib/mg400/calibration/cameras/` | Camera-to-robot homographies for each camera path |
| `/var/lib/mg400/calibration/microscope/` | Turret, autofocus, and reference-view data |
| `/var/lib/mg400/robot/stations.toml` | Taught robot stations |
| `/var/lib/mg400/robot/tool.toml` | Gripper tool offset |
| `/var/lib/mg400/stage/stage.toml` | Stage steps per mm, soft limits, named positions, and poses |
| `/var/lib/mg400/thermal/rois.toml` | Named thermal regions |
| `/var/lib/mg400/furnace/state.json` | Furnace sequence state |
| `/var/lib/mg400/runs/` | Run files and SQLite index |
| `/var/lib/mg400/recordings/` | Furnace recordings before archiving |
| `/var/lib/mg400/work/` | Gripper feedback, command files, persistent command locks, and mode-switch backups |

The installer creates `/var/lib/mg400/robot` with owner `1000:1000` and mode `0750` for tool and station data.
If `/var/lib/mg400/tool.toml` or `/var/lib/mg400/stations.toml` exists, it prints a move instruction and leaves that file unchanged.
Stop services and CLI processes that use the robot data before moving each old file into `/var/lib/mg400/robot` manually.
Do not overwrite an existing destination. Retain owner `1000:1000` and file mode `0600` or `0640`.
The installer preserves an existing `MG400_ORCH_TOOL_FILE` value. Update an old override before restarting its users.

The installer creates `/var/lib/mg400/stage` with owner `1000:1000` and mode `0700` for writable stage calibration.
It keeps `/var/lib/mg400` root-owned with mode `0750`.
If `/var/lib/mg400/stage.toml` exists, it prints a move instruction and leaves the file unchanged.
Stop the stage service before moving that file to `/var/lib/mg400/stage/stage.toml` manually. Do not overwrite an existing destination.
Retain owner `1000:1000` and file mode `0600` or `0640`. Update any old `MG400_STAGE_CONFIG` override before restarting.

Restore by hand on the new host:

1. Bring active lab work to a safe end on the old host. Stop services and disable the gripper collection request listener:

   ```sh
   mg400ctl stop all
   systemctl disable --now mg400-gripper-collector.path
   ```

   Stop any other process that writes host data before continuing.
2. Create the backup on the old host:

   ```sh
   mg400ctl backup /root/mg400-host.tar
   ```

3. Transfer the archive securely to `/root/mg400-host.tar` on the new host. Keep owner `root:root` and mode `0600`.
4. Prepare the new host according to [Prerequisites](#prerequisites), then install according to [Installation and updates](#installation-and-updates).
   Keep hardware disconnected during restoration. Before restoring data, stop the newly installed services and request listener:

   ```sh
   mg400ctl stop all
   systemctl disable --now mg400-gripper-collector.path
   ```

5. Restore only a trusted archive from this command. Inspect its members first:

   ```sh
   tar --list --verbose --file /root/mg400-host.tar
   ```

   Members must use relative paths for `etc/mg400/mg400.env` and `var/lib/mg400`, with no `..`, links, special files, or process-lock subtree.
   Confirm that the new host's restore paths contain no symbolic links.
   Restore numeric owners and modes:

   ```sh
   tar --extract --file /root/mg400-host.tar --directory / --numeric-owner --same-owner --same-permissions
   ```

6. Adjust `/etc/mg400/mg400.env` for the new camera device paths. Keep owner `root:root` and mode `0600`.
   The data paths above use owner `1000:1000` and file modes `0640` or `0600`.
   Keep directory mode `0750`, except the camera, stage and `calibration/cameras` directories, which require `0700`. Preserve the archive's owners and modes for other existing data.
7. If `/var/lib/mg400/work/gripper_feedback.json.command-lock.json` exists, a gripper command outcome is unconfirmed.
   Confirm the gripper state and preserve this file with owner `1000:1000` and mode `0600`.
   The collection service stays locked when it reads the restored file. Do not remove it to resume commands.
   Reconcile pending commands and saved run/furnace state with the actual instruments before starting services. Restoration must not replay commands.
8. Run the installer again after changing camera devices.
   Confirm that restored stations, tool offsets, stage settings, and calibration mappings match the hardware before motion.
9. Connect the robot network interface and USB devices, then start the selected services through the normal operating procedures.
